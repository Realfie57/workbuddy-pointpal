# 「检查更新」实现方案调研

> 结论先行：**方案一是可行的，限流真实存在但对你这个项目几乎不构成问题。**
> 而且有一个更省的办法——根本不用碰 API，靠 `github.com` 上的 302 跳转就能拿到最新版本号。

调研时间：2026-10-02 · 针对 WorkBuddy PointPal v1.2.13

---

## 一、限流是真实存在的吗？

**是，真实存在，但数值要分清。**

| 认证方式 | 限流 | 计数单位 |
|---|---|---|
| 匿名请求（不带 token） | **60 次 / 小时** | **按来源 IP** |
| 带 token / PAT | 5,000 次 / 小时 | 按账号 |
| GitHub App / OAuth App（企业云） | 15,000 次 / 小时 | 按应用 |

来源：GitHub 官方文档 [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
——「The primary rate limit for unauthenticated requests is 60 requests per hour.」

### 关键点：计的是 **IP**，不是软件、也不是用户

这一点是整件事的核心，也是最容易误判的地方：

> 「Unauthenticated requests are associated with the originating IP address,
> not with the user or application that made the request.」

也就是说，**同一个出口 IP 上的所有匿名调用共享那 60 次额度**。这会在这几种场景里出问题：

- 公司 / 学校 / 实验室网络（几百人共用一个 NAT 出口）
- 家庭宽带（运营商级 NAT，可能整栋楼共用一个 IP）
- VPN / 代理出口（同一个节点的所有人在分）
- CI 跑者池、云服务器

典型案例：NVIDIA 的 Brev CLI 安装文档专门写了一页
[CLI Install Fails with GitHub Rate Limit](https://docs.nvidia.com/brev/troubleshooting/cli-installation/github-rate-limit)
来解释这件事；Portainer 也踩过同样的坑——前端每次加载都查一次版本，
多管理员同时刷新就把额度打满了。

### 但为什么会存在「匿名 60 次」这个限制？

因为它是**反滥用设计**。GitHub 假设正常用户是「打开网页、偶尔点一下」，
60 次/小时对人是绰绰有余的。它防的是脚本疯狂抓取和 DoS。
所以它并不是「不允许你做更新检查」，而是「别高频轮询」。

## 二、对你的项目来说，这个限流影响大吗？

**结论：不大。算一笔账就清楚了。**

假设你的软件有 100 个用户，每人每天开一次机、每次启动检查一次更新：

```
100 用户 × 1 次/天 = 100 次/天 ≈ 4.2 次/小时（平均分布）
```

远低于 60。**而且是每人各自的家庭 IP 分别计数**，
一个普通用户家里就他一个人在跑你的软件，那 60 次/小时基本是他独占的。

真正会炸的只有两种情况：

1. **你的用户集中在一个大内网**（比如同一个公司/学校的几百人同时用）——
   这时他们共享出口 IP，可能撞额度；
2. **你做了高频轮询**（比如每 5 分钟查一次）——这是自找的。

所以：**只要「一天最多查一两次」，限流就不是问题。**

## 三、市面上的主流做法是什么？

### 做法一：直接用 GitHub Release API（最省事，很多人这么干）

```http
GET https://api.github.com/repos/OWNER/REPO/releases/latest
→ { "tag_name": "v1.2.13", "assets": [ { "browser_download_url": "..." } ] }
```

- ✅ 发新 Release 就自动生效，不用维护额外文件
- ✅ 能拿到完整的 assets 列表（下载链接 + 体积）
- ❌ 吃那 60 次/小时/ IP 的额度
- ❌ 拿不到「更新说明」以外的自定义字段（比如「强制更新」标志）

**谁在用**：大量中小开源项目、各类 CLI 工具。

### 做法二：静态 JSON feed（最可控，商业软件主流）

在仓库或自己域名放一个 `update.json` / `latest.yml`：

```json
{
  "version": "1.2.14",
  "url": "https://.../Setup-1.2.14.exe",
  "notes": "修了什么什么",
  "mandatory": false,
  "stagingPercentage": 25
}
```

- ✅ 不限流（走 raw.githubusercontent.com 或自己的 CDN）
- ✅ 可以放任意字段：强制更新、分阶段灰度、更新说明
- ✅ 可以脱离 GitHub（换域名、加 CDN、国内加速）
- ❌ **每次发版要手动同步这个文件**——你担心的正是这一点

**谁在用**：Electron 生态（`latest.yml` + electron-updater）、VS Code、
各类商业软件。Tauri / Zig 等新一代 updater 也统一走「签名 feed」这条路。

### 做法三：直接读 `github.com` 的重定向（最优雅，恰好解决你的顾虑）

**这是我这次调研最重要的发现。** GitHub 的 releases 页面有一个 302 跳转：

```http
HEAD https://github.com/OWNER/REPO/releases/latest
→ 302 Found
   Location: https://github.com/OWNER/REPO/releases/tag/v2.102.0
```

**关键点：这个跳转由 `github.com` 提供，不是 `api.github.com`，
所以完全不吃那 60 次/小时的 API 额度。**

我刚在本机实测验证过（2026-10-02）：

```
$ curl -sI https://github.com/cli/cli/releases/latest | grep -i location
Location: https://github.com/cli/cli/releases/tag/v2.102.0

$ curl -sI https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/releases/latest
Location: https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/releases/tag/v0.3.17
```

从 Location 里用一个正则就能抠出版本号：`/releases/tag/([^/?#]+)$`

- ✅ **零 API 额度消耗**（不受 60 次限制）
- ✅ **不需要维护任何额外文件**——发 Release 就自动生效
- ✅ 实现极简（一次 HEAD 请求 + 一个正则）
- ❌ 拿不到 assets 列表和更新说明（但下载链接可以按约定拼：
  `https://github.com/OWNER/REPO/releases/download/<tag>/<文件名>`）
- ❌ 如果哪天 GitHub 改了跳转格式，需要降级到 API

**谁在用**：`ida-hcli`（Hex-Rays 官方工具）专门提了 issue
[#316](https://github.com/HexRaysSA/ida-hcli/issues/316) 把这条列为**首选方案**，
理由就是「不消耗额度，且只在跳转格式变了时才需要降级到 API」。

### 做法四：Webhook / RSS

适合「你有服务器」或「只需通知自己」的场景，不适合桌面软件主动查更新。

## 四、给你的推荐：做法三 + 做法一兜底

结合你的实际情况（更新不固定、不想维护额外文件、用户量不大），**推荐做法三**：

```
① HEAD https://github.com/Realfie57/workbuddy-pointpal/releases/latest
     跟随重定向但不自动跳转，读 Location 头
② 正则抠 tag → 去掉前缀 v → 得到 "1.2.14"
③ 与当前版本（FileVersion）逐段比大小
④ 若更新：弹窗提示 + 打开 Release 页面（或直接下载）
⑤ 任何失败（超时 / 404 / 解析不出）→ 静默忽略，不打扰用户
```

**降级链**（按顺序尝试，全失败就放弃）：

```
先试做法三（302 跳转，零额度）
  ↓ 失败（格式变了 / 被墙）
再试做法一（api.github.com/releases/latest，吃额度但兼容性好）
  ↓ 失败
静默放弃，不弹任何错误
```

这样你**一个 JSON 文件都不用维护**，发 Release 就自动生效——
正好对应你「下次更新不固定、不一定会记得」的顾虑。

## 五、如果真要实现，这几个坑必须避开

### 1. 绝不能在启动路径上同步阻塞

国内网络访问 GitHub 经常超时，如果启动时同步等 5 秒，用户会以为软件卡死了。
**做法**：放到后台线程，或者干脆只在「关于」对话框里放一个手动「检查更新」按钮。

对你这个桌宠项目，我建议**手动触发**（关于对话框里一个按钮）为主。
理由：桌宠是常驻程序，用户很少主动去看版本；启动时弹更新提示反而烦人。
如果要做自动检查，加一个「启动 30 秒后检查一次，之后每 24 小时一次」的节流。

### 2. 失败必须完全静默

这是国内软件的生存法则。GitHub 在部分网络下不可达，
如果每次失败都弹「检查更新失败」，用户会骂人。**任何异常都吞掉。**

### 3. 版本号比较要注意

- `v1.2.13` vs `1.2.13`——前缀 `v` 要去掉
- `1.2.9` vs `1.2.13`——**不能按字符串比**（`"1.2.9" > "1.2.13"` 是 `true`！）
  要逐段转 int 比较
- 你的 exe 里已经有 `FileVersion`（`_asm_*.cs` 里的 `[assembly:]`），
  可以直接拿来比，不用在代码里写死版本号

### 4. 下载地址可以按约定拼

```
https://github.com/Realfie57/workbuddy-pointpal/releases/download/v1.2.14/WorkBuddyPointPal-Setup-v1.2.14.exe
                        └── 固定 ──┘                    └─ tag ─┘ └────── 文件名 ──────┘
```

所以只要**发布时文件名带上版本号**（你现在就是这么做的），
做法三拿不到 assets 列表也不影响下载。

### 5. 如果要自动下载安装，必须验签

否则中间人替换掉 exe 就完了。但对你现在这个阶段（用户量小、手动下载安装包完全可接受），
**建议先只做「提示有新版 + 打开 Release 页面」**，不做静默自动更新。
理由：自动更新要处理「下载到临时目录 → 关闭自己 → 替换文件 → 重启 → 自删」，
还要防杀软误报，复杂度远超收益。

## 六、一句话总结

| 问题 | 答案 |
|---|---|
| 限流真实存在吗？ | 真实。匿名 60 次/小时，**按 IP 计**，同一出口的所有人共享 |
| 对你影响大吗？ | 不大。一天查一两次的话，普通用户的家庭 IP 等于独占额度 |
| 主流做法？ | ①直接用 API（省事）②静态 JSON feed（可控，但你要手动维护）③读 `github.com` 的 302 跳转（**零额度、零维护**） |
| 建议？ | **做法三为主，做法一兜底**；手动触发优先于启动自动检查；失败全静默 |

**做法三完美契合你的顾虑**：不用维护 JSON，发 Release 就自动生效，
还顺带绕开了你担心的限流问题。
